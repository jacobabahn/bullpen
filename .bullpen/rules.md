- bullpen's command line is moving from Python to Rust, one group of commands per task (the plan: `rust-port-plan.md` in bullpen's briefs folder; `docs/code.md` says where things are). The Rust is one cargo workspace: `core/` (tasks, config, wording; never depends on `cli`), `cli/` (the program `bullpen`: the entry, its command table `cli/src/commands.rs`, and the commands moved so far) and `board/`. `bin/bullpen` is a small `sh` entry that runs the build (`target/bullpen`), which hands the commands Python still owns to `bin/bullpen-py`.
- The Python CLI is the `bullpen/` package (a module per feature over a small `core.py`, with no import loops; see `docs/code.md`), run by `bin/bullpen-py`. It's frozen during the port: change it only to fix a bug (and fix a twin's copy too: say both in the brief), or to delete what a port moved. Then `lua/watch.lua` (the Rex watcher, run with `rex do --all`), `prompts/` and `tests/` (a module per area; fake `rex`/`gh` and a local bare repo as origin in `tests/support.py`). Keep the style: small functions, plain wording in messages.
- Rust crates: `serde_json` (with `preserve_order`), `chrono` and `libc` for `core` and `cli`; no others without asking the person. Format `core` and `cli` with rustfmt (`cargo fmt -p bullpen-core -p bullpen-cli`, `max_width = 120` from `rustfmt.toml`); leave the board's formatting alone. Rust tests sit beside each module as `test_<module>.rs`.
- The repo may have no `origin` remote: bullpen has a local mode for that (no push, no PR; `accept` merges locally). Your change must work, or cleanly do nothing, in both modes.
- While you work, run the tests for what you're changing (`python3 tests/run.py <area or test name>`: it builds the command line first), `cargo test --workspace`, and for a port the compare cases (`cli/check/compare.sh [CASE...]`: it compares against the Python of the commit the branch started from; never point `BULLPEN_PY` at the live main checkout). Run the full suite (`python3 tests/run.py`) once, right before `ready`; it must pass, with new tests for what you add, in the module for their area. Reviewers never run the full suite: only the tests that check a claim.
- Document a change in the page for its topic under `docs/` (and `prompts/coordinator.md` if the coordinator should know), in the same plain style. Touch `README.md` only for install, the Quick start or its list of docs pages.
- Commits: no Co-Authored-By trailer, no mention of AI or Claude.
- A file stays under 1,000 lines unless there's a really good reason. New files stay under it. Don't add a new feature to a file that's already over (the board's `src/*.rs`, the bigger tests modules): put it in a new module where the code allows (the board's split is planned in BP-86). A reviewer flags a file pushed over 1,000 lines without a stated reason.
