- The Python CLI is the `bullpen/` package (a module per feature, the rest in `core.py`; see `docs/code.md`), run by the thin entry script `bin/bullpen`. Then `lua/watch.lua` (the Rex watcher, run with `rex do --all`), `prompts/` and `tests/` (a module per area; fake `rex`/`gh` and a local bare repo as origin in `tests/support.py`). Keep the style: small functions, plain wording in messages, no new dependencies.
- The repo may have no `origin` remote: bullpen has a local mode for that (no push, no PR; `accept` merges locally). Your change must work, or cleanly do nothing, in both modes.
- While you work, run the tests for what you're changing (`python3 tests/run.py <area or test name>`). Run the full suite (`python3 tests/run.py`) once, right before `ready`; it must pass, with new tests for what you add, in the module for their area. Reviewers never run the full suite: only the tests that check a claim.
- Document a change in the page for its topic under `docs/` (and `prompts/coordinator.md` if the coordinator should know), in the same plain style. Touch `README.md` only for install, the Quick start or its list of docs pages.
- Commits: no Co-Authored-By trailer, no mention of AI or Claude.
- A file stays under 1,000 lines unless there's a really good reason. New files stay under it. Don't add a new feature to a file that's already over (`bin/bullpen`, the board's `src/*.rs`, the bigger tests modules): put it in a new module where the code allows (splits of `bin/bullpen` and the board are planned in BP-78, BP-79 and BP-86). A reviewer flags a file pushed over 1,000 lines without a stated reason.
