- Layout: one cargo workspace. `core/` (tasks, config, wording; never depends on `cli`), `cli/` (the program `bullpen`; its command table is `cli/src/commands.rs`) and `board/`. `bin/bullpen` runs the build in `target/`. Then `lua/watch.lua` (the Rex watcher), `prompts/` and `tests/` (Python, a module per area; fake `rex`/`gh` in `tests/fakes/` (Rust, built by `tests/run.py`) and a local bare repo as origin in `tests/support.py`). `docs/code.md` says where things are. Keep the style: small functions, plain wording in messages.
- Run cargo as `bin/bullpen-cargo` (`bin/bullpen-cargo test -p bullpen-cli <name>`): plain `cargo` isn't on an agent's PATH.
- Crates: `serde_json` (with `preserve_order`), `chrono` and `libc` for `core`, `cli` and `tests/fakes`; ask the person before adding one. Format `core` and `cli` (and `tests/fakes`) with `bin/bullpen-cargo fmt -p bullpen-core -p bullpen-cli -p bullpen-fakes` (`max_width = 120` from `rustfmt.toml`); leave the board's formatting alone. Rust tests sit beside each module as `test_<module>.rs`.
- Tests while you work: only those for what you're changing (`python3 tests/run.py <area or test name>`, which builds the command line first; `bin/bullpen-cargo test <name>`). The full suite is `python3 tests/run.py` plus `bin/bullpen-cargo test --workspace`: run it once, right before `ready`, with its output kept in a file so a failure doesn't need a second run. It must pass, and new behaviour gets new tests, in the module for its area. Reviewers run neither in full: only the tests that check a claim.
- Never run or test against the main checkout (`~/dev/bullpen`): it is the bullpen that is running you. To compare with the code before your change, make a detached worktree at your merge-base and remove it afterwards.
- The repo may have no `origin` remote (local mode: no push, no PR; `accept` merges locally). Your change must work, or cleanly do nothing, in both modes.
- Document a change in the page for its topic under `docs/` (and `prompts/coordinator.md`, or the section for its setting in `prompts/coordinator/`, if the coordinator should know; a news line says what to do itself or fits a row of the guide's table, which the tests check), in the same plain style. Touch `README.md` only for install, the Quick start or its list of docs pages. If your change makes a line of `.bullpen/rules.md` untrue, fix that line in the same task.
- A file stays under 1,000 lines unless there's a really good reason, stated in your summary. Put a new feature in a new module, not in a file already over.
